# Changelog

All notable changes to this project will be documented here.

This project follows a practical changelog style: user-visible changes, safety changes, and release notes belong here; active task tracking belongs outside the repo.

## Unreleased

- **The README is a front page now, and it names the website.** It had grown to 915 lines and 12,500 words — every flag, edge case and error code of every command — which is more than anyone reads before installing. It is about 220 lines: what the tool does, install and setup, a quick start, the menu, one table of commands, what it won't do, the safety model in three tiers, the options most people need, and the contract for scripts. The detail it dropped lives where it is used — each command's `--help`, the guide at https://cli-tools-site.vercel.app/docs, and `skill/SKILL.md` for agents — and the website, until now only a badge under the title, is linked in the opening lines. It reaches the PyPI project page with the next release.
- **The bundled agent skill says what `--as-bot` runs.** Rule 9 of `skill/SKILL.md` said only `send` and `create topic` run as a bot and every other command refuses, so an agent asked to pin, react or ban as a named bot was told those refuse. It now lists what the tool runs as a bot: `send` (never `--at`), `create topic`, the message verbs but `read`, `unread`, `bookmark`, `draft` and `pins`, the five administration groups where the bot is an admin, `leave` and `watch`. The skill moves 1.23.0 -> 1.24.0.

## 3.36.0 - 2026-09-18

One change, and it is a behaviour change: every time you type is read in one stated zone.

- **A time with no offset is this machine's local time, everywhere.** `search`, `archive search`, `archive export` and `archive sync` read a bare `--since`/`--until` as UTC, and so did `--until` on `member mute` and `member restrict` and `--expires` on `invite create`, while `send --at` and `schedule post --at` read the same characters on this machine's clock; one help line of nine said which, and no menu prompt did. Local is now the one reading. **If you typed bare times into `--since`, `--until` or `--expires` and meant UTC, add a `Z`:** an offset or a trailing `Z` always wins, and nothing about a duration (`30m`, `7d`) changes.
- **A bare date is that whole local day,** from its first instant to its last. `archive search --until 2026-09-06` used to stop at the first second of that day, because the archive compares dates as text; the bound now reaches the store as the UTC moment it means, so `--until` is inclusive there as its help has always said.
- **A bare time takes the offset of its own date, not of today.** `--at 2026-11-01T09:00` typed in September was read with September's offset and would have posted an hour early once the clocks changed.
- **Every help line and menu prompt that takes a time says so,** in the same sentence, and the `member mute`, `member restrict` and `invite create` previews echo the moment they resolved with its offset spelled out (`Until   2026-09-06T14:30:00+02:00`), as `send --at` already did. Everything written for machines stays UTC: `--json`, exports, the archive and the audit log.

## 3.35.0 - 2026-09-18

The final wave of this cycle: the shared core at v0.14, one new read verb, and the small faults the live menu campaign left on the board.

- **`message pins` lists what a chat, or one of its forum topics, has pinned.** Newest message first, each row in `search`'s format. There is no pin time, because Telegram records none, and `--as-bot` refuses it, since Telegram marks `messages.search` users-only.
- **A forum's chat-level watch cursor is retired instead of replayed forever.** Every event in a forum carries its topic's rid, so a cursor stored under the chat's own rid by an older version could never advance, and each `watch run` walked the whole forum again. Nothing else is retired: not a chat without topics, not a topic, and never a chat that would not resolve.
- **A dropped event shows.** The runner's log names an event the engine discarded before any rule ran, with its reason; `watch status`' Last tick counts a drop, so a runner that discards everything it receives no longer reads as one that did nothing; and `watch run` prints what it did when it stops.
- **`archive search --query campaign-alert-721` finds its row.** A query FTS5 cannot parse is searched again as the words it is made of, and `deploy AND` or an unbalanced quote finds nothing instead of raising. Deliberate FTS5 syntax still means what it says.
- **Every archive readback goes through the shared store's own methods** rather than SQL spelled here. Bookmarking a message that already has a bookmark relabels it and keeps the original `created`, and an exports directory you keep at 0755 stays 0755 when an export lands in it.
- **A write Telegram refuses leaves one `failed` line in `audit.jsonl`,** like every other executed write. A write this tool refused before the call still leaves nothing.
- **A refusal reads like a refusal in both modes.** A write Telegram refuses now ends on an `error:` line naming Telegram's own error, with its hint, and exit 2 in human mode, instead of a raw Telethon traceback and exit 1; a bug in the tool itself still raises. An archive search the store refuses (a query with no words, a regex that will not compile) prints `error:` and its hint with no usage block, and under `--json` one refused envelope with `CONFIG_INVALID` instead of an empty stdout. Both found by the live test of this release.
- **`settings set`, every `admin`, `member` and `join-requests` write, and a `structure apply` that edits topics report what Telegram holds after the write,** not a copy served from before it. `settings set --forum` can now report a change at all.
- **The preflight asks the right question of the right chat.** It names the chat it actually checked (the `--to` chat for a forward or a copy), asks for `send_media` when a send carries a file, stops refusing pins, invites and renames that a chat's own defaults allow, treats a plain-text ban and an expired restriction correctly, and no longer tells you to ask an admin of a direct chat.
- **`message react` keeps the reactions you already hold on a message** instead of replacing them, within the one (or three, with Premium) Telegram lets an account hold. If Telegram refuses the longer set it keeps the new reaction and says which came off.
- **A profile with no record of which account it is records it the first time a run has already asked Telegram,** so a login made before profiles existed stops being unsigned without anyone running `auth`. Nothing already recorded is ever replaced.
- **A hint that names a profile prints the command with `--profile <name>` in it,** so following it acts on the profile it named instead of on `default`. The hints for the `qr` and `proxy` extras print `pipx inject` when the tool was installed with pipx.
- **The Watch screens tell the truth.** The rule form no longer promises a prompt it never asks, the name and scope rows name their two traps, `watch status` says nobody holds the lock instead of claiming there is no lock file, `schedule list --chat` says when Telegram holds nothing, and the review queue labels its date `sent=`. A `watch run` teardown that fails for an unexpected reason now says so instead of vanishing.
- **Smaller wording.** A message preview row says its time zone (`2026-09-05 10:00 UTC`); a typed `n` at any y/N prints `Answered no - cancelled.`, as a blank answer already did; two menu prompts say one thing about a blank; and the Create, Delete, Leave and My bots screens name the group they were opened from (`Main › Build › Create`).

## 3.34.0 - 2026-09-18

Twenty-one defects the live menu campaign of 2026-09-17 and 2026-09-18 found, fixed on branches of their own and merged together.

- **A dry run the tool refused never offers to do it for real.** All eight of the menu's dry-run gates asked "did the dry run come back with nothing?", and nothing is only the error the menu had already caught and printed — so a dry run that exited 1 (cancelled, partial), 2 (refused), 3 (a gate with no terminal) or 130 (interrupted) fell straight through to the *Dry-run done* screen and its *do it for real* row. It held for every one of them: `delete`, `clear-messages`, archive retention and forget, `structure apply`, `leave`, the typed Manage verbs and folder delete. One helper now runs the dry run and answers yes on exit 0 alone, and all eight gates ask it. The same red test caught a second defect on that path: after a refused ban, kick, demote, topics-off or folder delete, typing `0` at *Enter = menu, 0 = exit* redrew the group's screen instead of exiting, because those flows handed back the value the leave flow reads as "go back".
- **A refusal from the shared tree lands on the Failed screen instead of ending the menu session.** *Watch > Runner > Stop* with no runner running printed `no runner holds the lock` and then the whole menu exited: the errors the menu catches were named one by one and the shared tree's own refusal class was not among them, so nothing between the row and the process caught it. An archive retention or forget dry run against a scope the archive does not hold did the same. Such a refusal is now caught like any other, and the error line reads the envelope rather than the exception, so the code prints once with its hint under it — before, the code printed twice and the hint was dropped entirely.
- **The menu never opens a second Telegram session to find out who it is.** A profile whose login predates named profiles has no record of which account it is, so every identity lookup fell back to opening a client on the very session file the menu is holding — the lock error this tool has a named class for. *Review > Approve* died before its picker could draw, and the offline schedule list died once a chat picker had opened the session, both inside the menu's own process. The menu now asks the client it already holds, keeps that identity beside its banner and hands it to every command it runs; `watch status`, `stop` and `reload` read the profile record and never connect at all, and a profile with no record runs unsigned and says so rather than buying a decoration with a second session. `watch run`, which connects detached precisely so a one-shot command in another terminal keeps working, was asking who it was through a second session too — and so refused on exactly the profile that design exists for; it now asks its own detached client, after the connect.
- **`clear-messages` says what each topic holds, in topic ID order.** An all-topics dry run scanned the topics in one order and ticked them off in another, then printed a single total, so which topics the messages were actually in could only be found by searching. Both lists now go through the same ID ordering before the walk, and each scan line carries that topic's own count once the IDs are in (`Scanning topic 2 (1): 13 to clear`); the rows add up to the total, because a message already found is not counted twice. The recheck after the typed `DELETE` sorts its fresh list the same way, so an ID-ordered plan can never read Telegram's own order back as drift. The `--json` result gains a `topics` list — one `{id, title, matched}` row per topic — beside the four keys it already carried.
- **The write preflight confirms send, media and topic rights from what Telegram actually returns.** Telethon's permissions object spells `is_creator`, `is_admin` and the admin flags and has no `send_messages`, `send_media` or `manage_topics` at all, and the probe read rights by attribute name — so it could never confirm those three. Every live send, reply, forward, copy, poll, topic create, scheduled post, topic setting and topic-step apply came back "preflight could not confirm", the chat's own creator included, and a direct chat reported a `ValueError` reading permissions. Each right is now read where Telegram puts it: a creator holds everything; an admin's `manage_topics` comes off its own admin rights, it posts in a broadcast channel only with `post_messages`, and it sends in a group whatever its members may not; a member posts nothing in a broadcast channel or once it has left, and otherwise holds a send right unless its own banned rights or the chat's defaults take it away. A direct chat is not asked about at all — it holds the send rights, pin and delete. An unbanned member's `manage_topics` stays unconfirmed on purpose, because Telegram's own documentation disagrees about it. Refusals by name are unchanged.
- **A warning reaches the person running the command, before its gate.** Thirteen places raise a warning before a write — an unconfirmed right, rules that will not load — and every one of them went only into the `--json` envelope, so in normal use they went nowhere. Release 3.25.0 settled this one layer up for the readback sentence; warnings are the other half of it and were missed. A warning now prints as `warning: <sentence>` the moment it is raised, which on every write is before the preview and before the gate, dry runs included: a warning read after the title has been typed has arrived too late to be one. It prints in the menu too, and unlike the readback it prints in machine mode as well, on stderr — the envelope is for the agent, but a gate that needs a terminal still has a person reading there. Nothing prints when nothing was raised, and a repeated warning prints once. The preflight's own warning is reworded for the moment it now arrives: it says Telegram decides when the call goes out, rather than reporting a write that has not happened yet.
- **A topic rename reads back the title Telegram set, not a stale one.** A `settings set --topic` rename landed on Telegram and then printed *no field changed*, writing the old title into its result and its audit line: the read fired straight after the edit and was served the topic as it had been. The readback now reads the service message the edit itself posts and takes the fields that message names; a field it does not name is re-read after a bounded wait before the answer is believed, so an edit Telegram never applies still honestly reads *no field changed*. Setting or removing a topic's icon read back `unverified (TypeError)` on any topic that had no icon, even on a perfectly fresh read; it no longer does.
- **A folder title past Telegram's twelve characters is refused by name, before the preview.** Renaming a folder to a thirteen-character title printed Telegram's bare `Message was too long (caused by UpdateDialogFilterRequest)` after the `y`, with no hint and nothing naming the title. `folders create` and `folders edit` now hold `--title` to twelve code points — the limit Telegram's own constructor documents, and the one its desktop client counts — and refuse before the preview and the gate, on the CLI, under `--json` and in the menu, naming the title, its length and the cap. As a backstop the too-long error from Telegram itself is mapped to the same named refusal, so a cap Telegram lowers later still reads as a sentence rather than a traceback.
- **The Manage and Folders screens say what happened, in words.** `invite revoke` blanked the very link its `y/N` was about while the result printed it whole; the human preview now shows the link the person typed, and the plan, the envelope, the audit line and a `--json` run's stderr keep the redaction. Its readback printed `the link is revoked: True` and now names the chat and the link's title. `invite list --revoked` says *revoked* in its header and in its empty line. `admin list` printed no rights on the creator's row although the row promises them; the creator's rights now print like an admin's. A folder's card and its edit readback named chats by rid where the preview had named them by title; both now use the titles the run resolved, and a chat this run never resolved — one an edit dropped, a pinned chat — still reads as its rid. In the menu, a list or show form's run row said it would show a preview and then ask, though a read asks nothing; the settings-show topic row and the invite expiry row each carried their own hint about blank beside the prompt's, so the two contradicted each other; the folders list row promised chats that list never prints; and a label longer than 44 characters pushed the value column out of line.
- **A finished `send` or `message` verb says what it did in one sentence, instead of printing its result as JSON.** After the `y`, a person read the `Read back:` line and then an indented mapping of keys; a declined gate and a `message delete` dry run printed the mapping too. The `Read back:` line could not simply replace it — it is what was read, not what was done, it carries no id when it is unverified, and an `--at` send's message id, the one `schedule cancel` needs, lived only in the JSON. Each now prints one sentence above its kept `Read back:` line, in human output only: `Sent message 9001 to Agency (-100…).`, with the files it carried and the message it replied to, and for `--at` the scheduled id and the time Telegram holds it for. All fifteen message verbs say it the same way, naming the place exactly as the banner names it. A bare `unreact` says *your reactions*, because an empty reaction list takes every reaction of this identity off the message; `unreact --emoji` names the one it took off, which is the entry below. A declined gate and the delete dry run now print nothing extra at all. Under `--json` nothing moves: the result keeps every key, and the sentence is on neither stream.
- **`archive status` names the scopes an older text rendering wrote.** The shared tree stamps every scope with the rendering that wrote it, and the screen for it shipped in 3.26.0 and 3.27.0 — but this tool never declared which rendering it was, so the store stamped nothing and every status said no rendering version is declared: a fix that was inert in the tool it was built for. The tool now declares it, and the screen has something to say, on the CLI and on the menu's status row alike: a scope holding rows an older rendering walked is named with its message count and the command that rebuilds it. No release stamped a scope before this and the store keeps no per-row writer version, so every unstamped scope holding rows reads as behind until a sync or a `--full` walk covers it whole — it counts and never rewrites, because a rebuild refetches from Telegram and costs. Second, a markdown or HTML archive export now carries the marks its rows have everywhere else: `[fwd …]`, `[poll]`, `[file] …` and `[event] …` sit in front of the text in `archive export --format markdown`/`--format html` and in `search --archive --output` of either, so a forward and a copy of the same message stop exporting as one row twice. `json`, `jsonl` and `csv` are untouched, and `[media]` is left to the media column that already counts the file. That is the decision 3.28.0 named and deliberately left open.
- **`message unreact --emoji` takes off the reaction it names and leaves this account's others on the message.** Telegram's `SendReactionRequest` replaces an identity's whole reaction set, and `unreact` sent an empty list whatever was asked — so `--emoji 👍` on a message this account had also reacted to with 🎉 took both off, while `--help` said `--emoji` names the reaction to remove. The set to send is now built from the message's own reactions, read in the preflight and already carried on the brief, so there is no second fetch: `react` sends the one named, a bare `unreact` the empty list as before, and `unreact --emoji` sends this identity's *other* reactions back — its own only, because another account's reaction sent here would be claimed as this one's. The sentences follow: a bare `unreact` still prints `Removed your reactions from message N`, a named emoji prints `Removed 👍 from message N`, and the readback reports `carries no 👍 of yours` rather than claiming every reaction is gone. No help text changed — the fixture already described this behaviour; only the code did not do it. `message react` has the same bug in reverse on an account that may hold several reactions, and is filed on its own.
- **The banner names the account without putting part of its phone number on every screen.** An account with no username fell back to its display name plus the last two digits of its number, so `Acting as: -- (…NN) · account` sat on every screen of a live session — and on every screenshot of one. The distinguishing half is now the user id, which this tool already prints in every `tg:user:` rid it resolves and which tells two accounts apart absolutely where two digits only mostly did: `-- (user 4242)`, and `Sven (user 4242)` where the name alone used to stand. The helper that read the number is deleted with it, so nothing in a label reads it at all. Two smaller faults from the same run go with it: `doctor` called the pre-profile session `OK` while carrying the `auth --migrate` hint, which reads as nothing to do on the one screen that mentions the move — it is a `WARN` now, and a `WARN` is not a failure, so the exit code is unchanged; and a bot with sixty-odd commands dumped the whole list above its own screen title in *My bots*, pushing the title and its rows off a 24-row terminal — the profile takes a cap, the menu passes eight and the line under them names the command that prints every one, while `bots --bot` itself still prints them all.
- **A run under a named profile stamps that profile on its envelope, its plan and its audit line.** The identity behind a command was built with the profile argument's default, so every command run with `--profile work` signed the wrong login: the envelope's `identity` mapping, the `Identity` the plan is handed, and each audit line it signs all read `default` — and an audit trail kept on a second account was wrong for as long as it existed. The reporter now carries the profile the run resolved, from the config that was actually settled rather than from the raw flag, and the acting identity reads it back, so the three surfaces share the one identity they always shared and it names the right login. Nothing changes on the default profile, and the banner never printed the profile at all.
- **A mute, a restriction or a ban names every right Telegram will take, before the gate answers for it.** Telegram widens one banned right into the family beneath it and the previews never said so: live, `Takes send_messages` read back as fifteen rights, `Takes send_media` as seven, and the ban preview named no right and no duration at all while the write took all twenty-three and stored the 32-bit time ceiling as its end. The preview is the screen a `y` answers, so understating it approves less than it takes. A table now holds the widening — `send_media` over the six media kinds, `send_messages` over every send right including `embed_links`, `view_messages` over every right there is — and both the preview and the plan read it; the same table upwards names the `other` flag Telegram sets for itself on any promotion, which no preview mentioned. What reaches Telegram is still exactly what was asked for, and the hierarchy check still reads exactly that, so an actor without `other` can still promote; only the plan and the screens widen. The ban preview now says it takes every right there is, `view_messages` among them, and that it is permanent, and `2038-01-19T03:14:07Z` reads as *permanently* on the readback and in the member list while the JSON field keeps the date. Telegram documents no expansion rule anywhere, so the table is written from the live readbacks and its own comment says so. Two smaller ones from the same run: the typed gate asked for `@campaigndummybot` while every screen around it printed `campaign dummy (@campaigndummybot)`, so the prompt now names the label the screens print and the short form is still taken; and `admin rights` help said it set exactly the rights you name, which it now admits is plus Telegram's own `other`.
- **Leaving the runner's *Done* screen prints the *Done* screen and nothing else.** Quitting the watch runner printed `Task was destroyed but it is pending!` lines and a `RuntimeError: Event loop is closed` under the screen that had just said the run was over. Telethon's `disconnect` is not a coroutine while a loop is running: it puts the teardown on the *calling thread's* loop and hands back a shield over it, so the bridge built the teardown on the CLI's loop, the future it got back was refused by a `TypeError` that the teardown's bare `except` swallowed, and the disconnect was never awaited at all. It is now submitted as a coroutine to the client's own thread and awaited there, and the bridge's loop cancels and settles whatever is still on it, and shuts its async generators down, before closing — which is what makes a disconnect that times out quiet too. Every fake in the suite has an `async def disconnect`, which is why 1464 tests passed over this; the new check runs the bridge up and down in a child process and asserts its stderr is empty, because the noise comes from the garbage collector at interpreter shutdown, where nothing in-process can catch it.
- **Every hint naming `--profile` puts the flag where the parser takes it.** `--profile` hangs off the root parser, so `telegram-tools auth --profile work` dies in an argparse usage dump — exit 2, `unrecognized arguments: --profile work` — while the same command with the flag before the verb runs. The broken form is what `LOGIN_REQUIRED` printed, including as the envelope's `error.hint`, which is the one line an agent copies when a profile is not logged in. The hint now carries the flag before the verb, and README's *More than one account* block no longer contradicts the line under it. The guard is a test that parses every module with `ast`, so an f-string split across source lines is rendered whole — which is where a per-line grep gives up — takes every string naming both `--profile` and a `telegram-tools` command out of the source, the README, AGENTS.md, CONTEXT.md and `skill/SKILL.md`, and asserts the real parser accepts each one with the flag inside the command rather than beside it. A placeholder standing where the verb goes counts as a verb, and the doc lines are read the way a shell reads them, comments dropped. Two anti-vacuity tests fail if either extractor stops finding its known sites. Any later change adding a verb-then-flag hint turns it red, and the fix there is to reorder the flag rather than to weaken the test.
- **The runner alerts on a message that arrives while it is running.** It only ever alerted on what its start replay picked up: Telegram hands each update to exactly one of an authorization's active sessions, chosen at random, so any second telegram-tools connection on the same login won the draw and the runner's socket received nothing at all. The runner now holds the login alone while it runs, and a message from another sender fires its rule within a second, in an ordinary topic or in General.
- **A message posted with a time reaches Telegram's own scheduled queue.** `send --at`, with or without a file, passed Telethon a keyword it does not have, so every Telegram-side scheduled send died with a `TypeError`; the fakes swallowed the keyword, which is why the suite never saw it. The keyword is now the one Telethon takes, the fakes check every keyword against Telethon's real signature, and *Watch > Schedules* lists the entry as `Held by Telegram (server-held)` until it posts. Runner-held schedules were never affected.
- **A forum's General topic has one name, `tg:topic:<chat>:1`, and every path uses it.** Telegram sends no reply header for a message in General, so the runner scoped it to the bare chat rid while `archive sync` used the topic rid, and a rule scoped to the topic never matched a General message. The topic rid wins, because a forum has no chat scope at all; the chat rid is no longer reachable for a forum.
- **A login on the default profile after a logout keeps its session in the profile's own directory.** With the record gone, a fresh `default` was read as this machine's pre-profile login whatever was on disk, so every login after *Move the pre-profile session into a profile* wrote the new session back to the old path and the move was offered again forever. The old path is only `default`'s when that file actually exists.

## 3.33.0 - 2026-09-17

Three defects the live menu campaign found on 3.32.0, fixed together.

- **`clear-messages` on a topic clears the topic's newest message too.** `ForumTopic.top_message` is Telegram's *newest* message in a topic, not the message that opened it, and the collector skipped both it and the opener — so the most recent message in a topic survived a clear that said it had removed everything. A dry run against a topic holding four real messages reported three, and the live poll sitting at the top of it would have been left there. Only the opener is skipped now, because deleting the opener deletes the topic; the General topic, which has no opener, keeps its first message the same way. What the gate asks and what the readback reports are unchanged.
- **A refusal prints the way out, on the menu and on the plain CLI.** Every refusal this tool names carries a message *and* a hint — transfer ownership, run `delete`, ask an admin — and until now the hint reached only the `--json` envelope. On the CLI a `CommandError` fell through to `parser.error`, which printed argparse usage plus the message and dropped the hint; on the menu, `write_error` printed the message alone. Usage text is for a flag argparse never heard of, not for a command the tool understood and would not run, so `main` now catches the refusal first and prints `error:` and, under it, `hint:` on stderr, with no usage line. The exit code is the one the envelope carries: 2 for a refusal, 3 for a gate with no terminal, and 130 for `auth`'s own `INTERRUPTED`, which used to read 2 only because argparse swallowed it. The menu prints the hint under the message at all three of its error landings, so every hinted refusal in the tool is fixed in one place.
- **`search --topic` on a topic the chat does not have is refused by name.** It printed forty lines of Telethon ending in `RPCError 400: TOPIC_ID_INVALID`, exit 1, where every other bad target has always been refused in one sentence. Telethon 1.45 has no class for that error, so the bare `BadRequestError` is caught on the topic branch and raised as `TARGET_NOT_FOUND` naming the topic and the chat, with a hint listing the topic IDs the chat really has — read once, only on the refusal, and a chat whose list cannot be read still refuses and points at `discover`. Exit 2, and a refused envelope under `--json`. `search --output` shares the path, so export is covered by the same catch.

## 3.32.0 - 2026-09-16

- **A chat's creator is told `leave` cannot work, instead of being told it did.** Telegram has no call that takes the creator out of its own supergroup, channel or basic group: `channels.leaveChannel` from the creator returns without an error and without effect, which is why the official clients offer only *delete* or *transfer ownership*. `leave` sent it anyway and reported `Left …`, `left: true`, exit 0 — on a group created by this account, which four minutes later still listed it as an admin with one member, its creator. It now refuses before anything is sent, in both modes, with `PLATFORM_UNSUPPORTED`, a message naming the chat and a hint pointing at ownership transfer or `delete … --execute` (at Telegram itself for a basic group, which this tool does not delete). Because the dry-run refuses too, the menu's Leave flow stops there and never draws its *Leave it for real* row. The dry-run's old creator note is gone with it: what it warned about is not a cost any more, it is a refusal.
- **A leave Telegram will not confirm is no longer reported as done.** The readback was already run and already said `unverified`, and the status, the `left` flag and the exit code ignored it. When it cannot confirm — Telegram still listing this account in the chat, a cache answering — the status is now `partial`, `left` reads `"unverified"` rather than `true`, the human line says the leave could not be confirmed, and the exit code is 1. A confirmed leave is unchanged: `Left group … (…)`, `ok`, exit 0. This is the shape `structure apply` already reports when its own readback comes back unverified.

## 3.31.0 - 2026-09-16

- **The remap of an apply lists what it made.** `structure apply` of a blueprint carrying a topic written by hand — an object no export produced, so it has no source id, and the one object the apply must create — reported `ok`, made the topic, and then printed a remap of rows for objects that already existed and matched, with nothing for the id it had just minted. - **The runner is yours to operate, and it does not take your login.** `watch run` runs in the foreground; the tool neither installs nor prints a launchd or systemd unit. It takes an exclusive lock, so a second one exits 2 with `RUNNER_LOCKED` naming the holder, before it connects. It copies your profile's authorization into memory rather than opening the session file, so `telegram-tools send` in another terminal keeps working while it runs. On start it replays each scope from its cursor with duplicate suppression on: an event seen before the last exit fires nothing, one the exit swallowed fires once. The lock is `fcntl`, so `watch run` supports macOS and Linux and exits 2 with `PLATFORM_UNSUPPORTED` on Windows, where every one-shot command still works.
- **Two guarantees for a message posted later, and the tool always says which.** `send --at 2026-09-09T09:00` hands the message to Telegram, which posts it with this machine off: **server-held**. `schedule post --at | --every` stores a row **this runner** posts, and every listing spells out `runner-held: fires only while watch run is up on this machine`; Telegram has no repeat of its own, so `--every` is always that kind, and it takes an interval (`15m`, `2h`, `1d`) or a five-field cron expression. A time with no offset is this machine's local time and the tool echoes it back with the offset applied. `schedule list [--chat C]` shows both kinds with their guarantee, and `schedule cancel --id N [--chat C]` cancels either. Scheduling is account-only: `--as-bot` refuses `send --at` and `schedule` with `IDENTITY_MODE_UNSUPPORTED`, naming them. Watching is not — a bot receives updates for the chats it is in, so `--as-bot watch run` works.
- **`doctor` reports the runner**: who holds the lock, the last thing it logged, and whether the rules load — because a rules directory that will not load is a `watch run` that would refuse to start, and this is where you find that without starting one.
- **Menu.** Root row 7, `Watch`, now opens four screens: *Rules* (a form carrying every flag the command takes), *Runner*, *Scheduled* and *Review queue* — whose six rows are unchanged, one screen deeper. The root screen itself is unchanged, so no transcript is re-recorded.

- The row before the point of no return read `Delete it for real (asks you to type Hermes)`, and a tester typed the title at that screen, where only a row number is an answer. It now reads `Delete it for real - the next screen asks for its exact title`, which says when.


- `delete` removes the group, channel or topic itself, not just the messages inside it. The tool could make all three and take none of them back, so a forum scaffolded with telegram-tools could only be unscaffolded in the Telegram app. `telegram-tools delete group|channel|topic` closes that with a gate one notch tighter than `clear-messages`: dry-run by default, and the real run wants `--execute` **and** the target's own title typed back, not the word `DELETE`. For a whole chat the mistake worth catching is deleting the *wrong* one, and only the title catches that. There is deliberately no `--yes` anywhere on the path: an agent can search, send and clear unattended, and can never delete a chat.

- Naming the kind is a second lock, checked against what Telegram says rather than what you typed. `delete group` pointed at a broadcast channel is refused before anything is asked, naming the real type. The preview says how far the deletion reaches and does not soften it: a group or channel goes for **every** member, not just for you, along with every message, its invite links and its ID, and only its creator can do it at all.

- `delete` removes exactly what `create` makes, so no cleanup this tool performs is a one-way door. Supergroups (with or without topics), broadcast channels and forum topics are all deletable and all creatable. A **basic group** is deliberately refused with that reason stated: `create` makes supergroups and cannot make a basic group back, so `delete` will not take one away — Telegram itself still can.

- Deleting a topic is honest about the mechanism. Telegram has no delete-topic method; a client removes a topic by deleting every message in it, the service message that opened it included, after which the topic is gone from the list (`messages.deleteTopicHistory`). That is what `delete topic` does, and the preview says so. The **General** topic has no such opening message and cannot be deleted at all — it is refused with a pointer to `clear-messages`, which empties it instead.

- The menu carries the same flow, and never as a shorter path past a gate. *Delete a group, channel, or topic* is a new root row: it works out the kind from what you picked rather than asking you to name it, dry-runs first, and only then offers a row that tells you which title it is about to ask for. A typed ID or `@username` is the one case it asks, because nothing has looked it up and guessing is not a gate.

- One new root menu row shifts the numbering: *Delete* is 5, *Clear topic messages* moves to 6, *My bots* to 7, *Check setup* to 8.

## 3.5.1 - 2026-08-31

- The menu's chat picker lines its ID column up after an emoji title. Padding counted codepoints while the terminal draws columns, so `📚 Vaults` (8 characters, 9 columns) and `⚠️ Alerts` (9 characters, 8 columns) had their IDs two columns apart, and a picker with a few emoji titles read as ragged. A new `columns` helper measures a title the way a terminal actually draws it and cuts a long one on a column boundary rather than through an emoji. The rules are measured, not assumed: an emoji is two columns from one codepoint, a variation selector such as U+FE0F draws nothing and does not widen what it follows, a zero-width joiner draws nothing, and each half of a flag draws two. Fourteen shapes -- plain text, CJK, a combining mark, emoji with and without U+FE0F, a flag, a skin-tone modifier and two ZWJ sequences -- were checked by printing each one and asking the terminal where the cursor landed. Nothing else in the repo pads a name: every other column pads a numeric ID or puts the name last.

## 3.1.0 - 2026-08-14

- Add `bots`: list the bots you own with their numeric IDs, show one bot's full profile, and edit its display name, bio, description, commands, profile photo, and default group/channel admin rights.
