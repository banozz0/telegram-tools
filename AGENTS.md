# telegram-tools — agent brief

Local Telethon CLI operating the user's own Telegram account: `discover` chat/topic IDs, `search`/export messages (five formats, or `--archive` offline), `archive` (sync a local searchable copy, search/export it, status, retention/forget), `review` (the links and files a sync noted: list/status offline, approve fetches into quarantine after a y/N, accept keeps a file after showing its verdict, reject, retry), `structure` (a chat's blueprint: export, diff, apply behind the typed title, remap), `admin`/`member`/`join-requests`/`invite`/`settings` (running a chat: admins and their rights, bans and bounded restrictions, join requests, invite links, slow mode; ban and demote behind the person's typed label), `watch` (rules over live events and the runner that fires them: run/status/stop/reload plus rules list/add/edit/remove/enable/disable/test), `schedule` list/post/cancel beside `send --at`, `send` a message (`--reply-to`, `--at`), `message <verb>` (reply, edit, delete, forward, copy, react, unreact, pin, unpin, poll, typing, read, unread, bookmark, draft), `create` group/channel/topic, `delete` the same three, `clear-messages`, `bots` (BotFather settings), `auth`/`profiles` (named logins), `doctor`. Global `--json`/`--jsonl` put one shared-schema envelope on stdout for agents, `--profile` picks the login, and `--as-bot NICK` runs `send` (never `--at`)/`create topic`/the message verbs bar read, unread, bookmark, draft/the five administration groups where the bot is an admin/`watch` as an owned bot (every other command refuses with `IDENTITY_MODE_UNSUPPORTED` before connecting); human output is untouched by them. Public repo — contributor-facing; never commit phone numbers, API hashes, tokens, or exported chat data (CONTRIBUTING.md binds).

## Working here
- Test: `.venv/bin/python -m pytest -q` → all pass (1056 as of v3.16.0), no network, no scanner binary. CI adds `compileall` + per-subcommand `--help` smoke; there is no lint step. `python-socks` and `segno` are the two optional extras (`proxy`, `qr`); the base install stays Telethon + dotenv, and each extra's absence must **refuse** a command, never degrade it.
- `src/telegram_tools/_core/` is **not this repo's code**: a copy of a shared tree at the tag in `_core/VERSION`. Never edit it — `tests/test_core_copy.py` fails on any local change. A fix goes to the source, then `CLI_TOOLS_CORE_PATH=<checkout> scripts/sync-core.sh <tag>`.
- Four tests are laws, not conveniences. `tests/test_help_surface.py` freezes every `--help` against `tests/fixtures/help/` — an added flag needs a named entry in `ALLOWED_ADDITIONS` (a dict keyed by the parser it applies to, so an addition on `send` cannot silently delete the same words from another parser's help) carrying its reason (the `auth` parser is captured as `login.txt`; the commit guard refuses a non-Markdown filename carrying `auth`, which is also why `login.py` is not `auth.py`). `tests/test_seams.py` fails if `src/`, README, AGENTS, CONTEXT or `skill/SKILL.md` names the sibling platform or the sibling tool. In `tests/test_menu.py`, `test_every_flag_has_a_row_in_the_menu_or_a_named_reason_not_to` holds spec §14's rule against the live parser (an exception goes in `NO_ROW` with its reason) and `test_the_menu_never_builds_a_skipped_confirm` keeps the menu off the short path past a gate.
- Every write builds a plan, preflights the rights it needs, re-derives the target after its gate, reads back, and appends one redacted line to `~/.telegram-tools/audit.jsonl` — from the menu as well. A new write does all five or it is not finished.
- The archive: `adapters/archive.py` is `ArchiveSource` over Telethon (a forum is its topics, never itself; the cursor is `top:low:open|done` because Telegram serves history newest first — CONTEXT.md explains), `archive.py` opens the store 0600-first and formats the screens, and every archive command but `sync` runs offline against the profile record's identity. `search --archive` maps the live flags onto archive scopes with no connection. `archive sync` writes only the local file and is read-only against Telegram, so it has no plan or audit line; `retention`/`forget` have both.
- The review queue: `adapters/media.py` turns a walked message's URL entities and its photo or document into `Candidate`s (the archive source collects them, `archive sync` enqueues them after the commit, nothing fetches them) and holds `TelegramMediaFetcher`, the `MediaFetcher` that re-reads the message and streams `iter_download` from an offset. `review.py` wires the shared pipeline (`_core/download.py`, eleven checks, `_core/scanner.py` ClamAV) with this tool's fetchers, limits from `config.json` and screens; the module-level `link_fetcher`, `resolver` and `scanner_factory` are what tests replace, so the suite has no network and no scanner. Both human gates refuse without a tty in either mode (`cli._review_io`, exit 3); `list` and `status` never contact a host.
- Structure blueprints: `adapters/blueprint.py` is `TelegramBlueprintPort` (`BlueprintPort`: `read` a chat through `channels.getFullChannel` and the topic walk, topics ordered by title because Telegram has no topic order; `apply` one step) and owns the rights primitives (default banned rights, slow mode, join approval, one admin's rights set) the P7 cards wrap. `structure.py` registers the one allowlist (`cli-tools/blueprint/telegram/1`; `admins`, `invite_links`, `linked_chat` excluded, so `never_transferred` is generated), holds the four-line no-perfect-clone banner, the screens and the plan. `apply` is `delete`'s gate and refuses without a tty in either mode; every accepted step audits through the port's `on_step`; `--create` goes through `create.create_group`/`create_channel`. A basic group is refused with the parity reason.
- Administration: `adapters/manage.py` is `TelegramManagePort` (participant reads through `channels.getParticipant(s)`, `channels.editBanned` for a ban, a restriction and lifting either, join requests, the three invite calls, the full-chat settings read; admin rights and slow mode go through the blueprint port's primitives, never a second spelling). `manage.py` holds the ops table (`OPS`: group, verb, approval, required rights), the parsers of `--until` (a minute to a year), `--rights` and `--slow-mode`, `require_hierarchy` (`HIERARCHY_DENIED` naming both rights sets), the typed-label gate and the screens; `cli._run_manage` is the one handler over all five groups. `member ban` and `admin demote` are `typed_name` and refuse without a tty in either mode; the other writes are `prompt_y` with no `--yes`. A ban's `--reason` lives in the plan and the audit line only, because Telegram has no reason field (section 16). Invite links reach only the `result` of `invite list` and `invite create`, through `Reporter.result(show_invites=True)`; everything else is redacted. `RIGHT_NAMES` carries `add_admins`.
- Watch and scheduling: `adapters/events.py` is `ClientLoop` (one Telethon client on a thread of its own, so the runner's step loop stays synchronous — core's `EventSource` and `MessageSender` are), `TelegramEventSource` (NewMessage, MessageEdited, ChatAction and the two reaction updates mapped to core `Event`s; one message is a `message` plus a `link` plus a `media` event, the scope is the topic in a forum, an edit's `edit_version` is its timestamp and a reaction's is a digest of the summary; `replay` walks `iter_messages(min_id=cursor, reverse=True)` and is account-only) and `TelegramMessageSender` (this tool's own send under `yes_allowlist`, `SendNotAllowedError` → `NOT_ALLOWLISTED`, `FloodWaitError` → `RateLimited`). `client.detached_session` reads the profile session's one authorization row read-only into an in-memory `StringSession`, which is why `watch run` and a one-shot command can be up at once. `watch.py` builds a `cli-tools/rule/1` object from the flags, holds the screens, and re-exports core's two guarantee strings rather than spelling a third. `cli._run_watch*` and `_run_schedule*` are the handlers; `_refuse_unrunnable` checks `fcntl` and a live holder before connecting. The rules tree goes through `make_private_tree` before core writes into it.
- Bare invocation is the human menu; agents pass a subcommand. Profiles, sessions, exports and the audit log live in `~/.telegram-tools/`, outside the repo, written 0600 in 0700 directories — every write refuses while anything there is group- or world-readable.
- The root menu is spec §14's nine rows and its numbers are a promise: row 4 (Build) holds create, delete and the four structure rows, row 6 (Manage) holds the five administration groups and row 7 (Watch) holds four screens — Rules, Runner, Scheduled, Review queue — so nothing renumbers again. Nothing is reserved now. Changing the grouping is gate G6 — Sven sees a transcript first. Re-record with `.venv/bin/python docs/transcripts/record.py` (a real pty, an invented account) and hand both files to `../cli-tools-site/docs/transcripts/`, then re-check the screen indices in its `src/pages/index.astro` and run `pnpm verify` there.
- `skill/SKILL.md` (independently versioned) is the bundled agent skill's source of truth: a CLI-surface change updates it **in the same commit** — convention, nothing enforces it.
- A user-visible fix also gets its CHANGELOG entry and version bump in the same change; unreleased fixes silently stacking on the last shipped version is the failure mode to avoid.

## Destructive commands
`clear-messages` deletes real messages: dry-run is the default, execution needs `--execute` plus typed `DELETE`. `bots` mutates live bot settings behind a diff + confirm (`--yes` skips). `send` posts publicly as the user behind a full-message preview + `y/N`; its `--yes` additionally requires the destination in `TELEGRAM_SEND_ALLOWLIST` (unset = every `--yes` send refused). `create` confirms before making a real, visible object. `auth` writes or removes a login: `--logout` needs the profile name typed back, `--migrate` a `y/N`, and it has no `--yes`, so it is interactive-only by construction — the skill tells agents not to drive it. `delete` removes the chat or topic itself: dry-run default, execution needs `--execute` plus the target's **exact title** typed back — for a container the mistake worth catching is the wrong target, not the absent intent — and it has no `--yes`, so deletion is never unattended. `archive retention`/`archive forget` prune the local archive: dry-run default, `--execute` plus the scope's exact title, no `--yes`. `message delete` is `clear-messages`' gate on a selection (`--ids` or `--from-search`, an archive query): dry-run default listing every id, `--execute` plus typed `DELETE`, no `--yes`, and bounded — above `--limit` (200) refuses with `BULK_LIMIT`, above 1000 needs `--i-know` and the count typed too; `messages.bound_selection` is the rule. Every other message verb is `send`'s gate, and its `--yes` needs the chat it *lands in* allowlisted (`--to` for forward/copy). `structure apply` makes topics and changes settings on a real chat and never deletes there: dry-run default, `--execute` plus the target's exact title, no `--yes`, and a terminal in either mode (`APPROVAL_REQUIRED`, exit 3 without one); `export`, `diff` and `remap` only read. `member ban` and `admin demote` are `delete`'s gate on a person: dry-run default, `--execute` plus the person's exact label (`@username`, else their name), no `--yes`, a terminal in either mode; the other administration writes ask `y/N` with no `--yes`, and every one refuses by name before the call when the right is missing or the hierarchy forbids it. `watch rules add|edit|enable|disable` write a local rule file and `remove` asks `y/N`; `schedule post` and `schedule cancel` ask `y/N`; none of the five has a `--yes`, because nothing unattended should write a rule or a schedule. A rule can never download or mutate: `_core/rules.ACTION_KINDS` is the closed six, checked when the file is written, and an alert to a chat goes through the same `TELEGRAM_SEND_ALLOWLIST` an unattended `send --yes` answers to. `watch run` installs no service, takes an exclusive `fcntl` lock (`RUNNER_LOCKED`), and is `PLATFORM_UNSUPPORTED` where `fcntl` is absent. `--as-bot` narrows and never widens: `BOT_MODE_COMMANDS` in `cli.py` plus `messages.BOT_VERBS` is the whole list of what a bot may run, the bot must be a member of the target (checked before the preview) and an admin of it for the administration groups, and `--yes` still needs the allowlist. Keep those gates, and keep the menu from ever being the shorter path past one.

Parity rule: `delete` removes exactly what `create` makes. Supergroups, broadcast channels and forum topics, yes; a basic group is refused, because `create` makes supergroups and cannot make one back. Telegram has no delete-topic method — a topic is removed by deleting all its messages including the one that opened it (`messages.deleteTopicHistory`), which is what `delete topic` does; the General topic has no such message and is refused.
