# telegram-tools — agent brief

Local Telethon CLI operating the user's own Telegram account: `discover` chat/topic IDs, `search`/export messages (five formats, or `--archive` offline), `archive` (sync a local searchable copy, search/export it, status, retention/forget), `send` a message (`--reply-to`), `message <verb>` (reply, edit, delete, forward, copy, react, unreact, pin, unpin, poll, typing, read, unread, bookmark, draft), `create` group/channel/topic, `delete` the same three, `clear-messages`, `bots` (BotFather settings), `auth`/`profiles` (named logins), `doctor`. Global `--json`/`--jsonl` put one shared-schema envelope on stdout for agents, `--profile` picks the login, and `--as-bot NICK` runs `send`/`create topic`/the message verbs bar read, unread, bookmark, draft as an owned bot (every other command refuses with `IDENTITY_MODE_UNSUPPORTED` before connecting); human output is untouched by them. Public repo — contributor-facing; never commit phone numbers, API hashes, tokens, or exported chat data (CONTRIBUTING.md binds).

## Working here
- Test: `.venv/bin/python -m pytest -q` → all pass (817 as of v3.12.0), no network. CI adds `compileall` + per-subcommand `--help` smoke; there is no lint step. `python-socks` and `segno` are the two optional extras (`proxy`, `qr`); the base install stays Telethon + dotenv, and each extra's absence must **refuse** a command, never degrade it.
- `src/telegram_tools/_core/` is **not this repo's code**: a copy of a shared tree at the tag in `_core/VERSION`. Never edit it — `tests/test_core_copy.py` fails on any local change. A fix goes to the source, then `CLI_TOOLS_CORE_PATH=<checkout> scripts/sync-core.sh <tag>`.
- Four tests are laws, not conveniences. `tests/test_help_surface.py` freezes every `--help` against `tests/fixtures/help/` — an added flag needs a named entry in `ALLOWED_ADDITIONS` carrying its reason (the `auth` parser is captured as `login.txt`; the commit guard refuses a non-Markdown filename carrying `auth`, which is also why `login.py` is not `auth.py`). `tests/test_seams.py` fails if `src/`, README, AGENTS, CONTEXT or `skill/SKILL.md` names the sibling platform or the sibling tool. In `tests/test_menu.py`, `test_every_flag_has_a_row_in_the_menu_or_a_named_reason_not_to` holds spec §14's rule against the live parser (an exception goes in `NO_ROW` with its reason) and `test_the_menu_never_builds_a_skipped_confirm` keeps the menu off the short path past a gate.
- Every write builds a plan, preflights the rights it needs, re-derives the target after its gate, reads back, and appends one redacted line to `~/.telegram-tools/audit.jsonl` — from the menu as well. A new write does all five or it is not finished.
- The archive: `adapters/archive.py` is `ArchiveSource` over Telethon (a forum is its topics, never itself; the cursor is `top:low:open|done` because Telegram serves history newest first — CONTEXT.md explains), `archive.py` opens the store 0600-first and formats the screens, and every archive command but `sync` runs offline against the profile record's identity. `search --archive` maps the live flags onto archive scopes with no connection. `archive sync` writes only the local file and is read-only against Telegram, so it has no plan or audit line; `retention`/`forget` have both.
- Bare invocation is the human menu; agents pass a subcommand. Profiles, sessions, exports and the audit log live in `~/.telegram-tools/`, outside the repo, written 0600 in 0700 directories — every write refuses while anything there is group- or world-readable.
- The root menu is spec §14's nine rows and its numbers are a promise: rows 6 and 7 are reserved for later packs so nothing renumbers again. Changing the grouping is gate G6 — Sven sees a transcript first. Re-record with `.venv/bin/python docs/transcripts/record.py` (a real pty, an invented account) and hand both files to `../cli-tools-site/docs/transcripts/`, then re-check the screen indices in its `src/pages/index.astro` and run `pnpm verify` there.
- `skill/SKILL.md` (independently versioned) is the bundled agent skill's source of truth: a CLI-surface change updates it **in the same commit** — convention, nothing enforces it.
- A user-visible fix also gets its CHANGELOG entry and version bump in the same change; unreleased fixes silently stacking on the last shipped version is the failure mode to avoid.

## Destructive commands
`clear-messages` deletes real messages: dry-run is the default, execution needs `--execute` plus typed `DELETE`. `bots` mutates live bot settings behind a diff + confirm (`--yes` skips). `send` posts publicly as the user behind a full-message preview + `y/N`; its `--yes` additionally requires the destination in `TELEGRAM_SEND_ALLOWLIST` (unset = every `--yes` send refused). `create` confirms before making a real, visible object. `auth` writes or removes a login: `--logout` needs the profile name typed back, `--migrate` a `y/N`, and it has no `--yes`, so it is interactive-only by construction — the skill tells agents not to drive it. `delete` removes the chat or topic itself: dry-run default, execution needs `--execute` plus the target's **exact title** typed back — for a container the mistake worth catching is the wrong target, not the absent intent — and it has no `--yes`, so deletion is never unattended. `archive retention`/`archive forget` prune the local archive: dry-run default, `--execute` plus the scope's exact title, no `--yes`. `message delete` is `clear-messages`' gate on a selection (`--ids` or `--from-search`, an archive query): dry-run default listing every id, `--execute` plus typed `DELETE`, no `--yes`, and bounded — above `--limit` (200) refuses with `BULK_LIMIT`, above 1000 needs `--i-know` and the count typed too; `messages.bound_selection` is the rule. Every other message verb is `send`'s gate, and its `--yes` needs the chat it *lands in* allowlisted (`--to` for forward/copy). `--as-bot` narrows and never widens: `BOT_MODE_COMMANDS` in `cli.py` plus `messages.BOT_VERBS` is the whole list of what a bot may run, the bot must be a member of the target (checked before the preview), and `--yes` still needs the allowlist. Keep those gates, and keep the menu from ever being the shorter path past one.

Parity rule: `delete` removes exactly what `create` makes. Supergroups, broadcast channels and forum topics, yes; a basic group is refused, because `create` makes supergroups and cannot make one back. Telegram has no delete-topic method — a topic is removed by deleting all its messages including the one that opened it (`messages.deleteTopicHistory`), which is what `delete topic` does; the General topic has no such message and is refused.
